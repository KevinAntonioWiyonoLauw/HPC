\chapter{PENDAHULUAN}
% =====================================================================

\section{Latar Belakang Masalah}

Sistem \keyword{Retrieval-Augmented Generation} (RAG) menjawab pertanyaan dengan lebih dulu mengambil potongan dokumen yang paling relevan dari sebuah basis pengetahuan, lalu menyusun jawaban berdasarkan konteks tersebut. Pada domain kepatuhan internal, proses pengambilan ini tidak boleh melewatkan pasal pengecualian atau ambang batas nominal. Karena alasan itu, proyek ini memilih \keyword{Exact} $k$-Nearest Neighbors ($k$-NN) dan bukan \keyword{Approximate Nearest Neighbor} (ANN), agar \keyword{recall} tetap 100\%.

Perhitungan \textit{exact} $k$-NN secara sekuensial pada CPU memiliki kompleksitas waktu $\mathcal{O}(Q \times N \times D)$, dengan $Q$ jumlah kueri, $N$ jumlah vektor basis data, dan $D$ jumlah dimensi. Pada skala ratusan ribu vektor, pendekatan sekuensial menjadi lambat dan tidak memenuhi standar latensi \keyword{real-time}. Ada dua \keyword{bottleneck} utama pada arsitektur komputer:

\begin{enumerate}[label=(\arabic*),leftmargin=2.2em]
  \item \keyword{Memory-bound}, yaitu matriks basis data berukuran ratusan megabita tidak muat di \keyword{L3 Cache} CPU sehingga terjadi \keyword{cache thrashing}.
  \item \keyword{Compute-bound}, yaitu instruksi aritmatika belum memanfaatkan paralelisasi data (SIMD) secara optimal.
\end{enumerate}

Proyek ini menjawab kedua masalah tersebut dengan pendekatan \keyword{High-Performance Computing} (HPC). Implementasi dan analisis komparatif dilakukan untuk algoritma \textit{Exact} $k$-NN menggunakan paralelisasi \keyword{shared-memory} (OpenMP), akselerasi GPU (CUDA), dan distribusi memori antar-simpul (MPI). Optimasi diarahkan pada satu permasalahan operasional yang konkret, yaitu lamanya penelusuran dokumen kepatuhan internal pada aplikasi \keyword{SIKA} (Sistem Informasi Kepatuhan Internal).

\section{Rumusan Masalah}

Berdasarkan latar belakang di atas, rumusan masalah dalam proyek ini adalah:
\begin{enumerate}[leftmargin=2em]
  \item Bagaimana karakteristik \textit{bottleneck} performa (latensi, \keyword{cache miss rate}, dan \keyword{instruction throughput}) dari algoritma \textit{Exact} $k$-NN sekuensial pada data berdimensi tinggi?
  \item Bagaimana memetakan dan mengoptimasi operasi jarak vektor memanfaatkan hierarki memori (\keyword{loop tiling} di CPU dan \keyword{shared memory} di GPU)?
  \item Bagaimana merancang distribusi data (\keyword{sharding}) dan komunikasi antar-simpul dengan MPI untuk memproses data yang melebihi kapasitas memori satu proses?
  \item Seberapa besar peningkatan performa (\keyword{speedup}) dan efisiensi skalabilitas yang dihasilkan OpenMP, CUDA, dan MPI dibandingkan \keyword{baseline}?
  \item Sejauh mana optimasi tersebut membawa \keyword{retrieval} pada SIKA memenuhi target latensi p95 $\leq 100$~ms, dan bagaimana wujud sistem yang mendemonstrasikannya?
\end{enumerate}

\section{Tujuan Proyek}

Tujuan dari pelaksanaan proyek ini adalah:
\begin{enumerate}[leftmargin=2em]
  \item Mengembangkan dan memprofil program \textit{baseline} sekuensial di CPU untuk mengukur latensi komputasi dan masalah \keyword{cache}.
  \item Mengimplementasikan paralelisasi \keyword{loop} dan vektorisasi (SIMD) dengan OpenMP.
  \item Mengembangkan \keyword{kernel} CUDA berbasis GEMM dengan \textit{shared memory} dan \keyword{parallel reduction}.
  \item Menerapkan pola \textit{sharding} dan \keyword{Gather} dengan MPI untuk menurunkan jejak memori per proses.
  \item Melakukan \keyword{benchmark} dan analisis metrik kinerja untuk membuktikan efektivitas setiap level arsitektur, dengan kriteria kelulusan yang ditetapkan sebelum pengukuran.
  \item Mengintegrasikan \keyword{engine} hasil optimasi ke dalam aplikasi SIKA yang dapat didemonstrasikan langsung, dengan \textit{engine} yang dapat ditukar saat berjalan.
\end{enumerate}

\section{Batasan Masalah}

\begin{enumerate}[leftmargin=2em]
  \item Algoritma difokuskan pada \keyword{Brute-Force / Exact Search} $k$-NN dengan \keyword{Euclidean Distance}. Proyek tidak mencakup ANN (HNSW, FAISS) dan tidak membandingkan akurasi \textit{Exact} terhadap ANN.
  \item Tipe data vektor adalah \keyword{single-precision floating-point} (\texttt{float32}).
  \item Dataset berupa matriks vektor berdimensi statis ($D=384$ atau $768$), sintetis maupun subset dataset publik, dengan jumlah vektor maksimum $500.000$.
  \item Skenario aplikatif diwujudkan sebagai purwarupa \keyword{single-node}. Aspek non-fungsional sistem produksi (autentikasi, ketersediaan tinggi, replikasi) di luar cakupan.
  \item Kualitas model LLM dan model \keyword{embedding} tidak dievaluasi dan diperlakukan sebagai komponen tetap.
  \item Evaluasi performa dilakukan pada lingkungan spesifik yang tersedia, didefinisikan pada Bab III.
\end{enumerate}

\section{Konsep \texorpdfstring{$k$}{k}-Nearest Neighbors pada Vector Database}

Sistem RAG mengandalkan pencarian informasi semantik melalui representasi vektor berdimensi tinggi (\keyword{embeddings}). Untuk menemukan dokumen yang relevan dengan kueri, sistem menjalankan algoritma $k$-NN untuk mencari $k$ vektor dalam basis data yang jaraknya paling dekat dengan vektor kueri. Untuk vektor kueri $\vect{q}$ dan vektor dokumen $\vect{p}$ yang berdimensi $D$, kuadrat jarak Euclidean dirumuskan sebagai:
\begin{equation}
d^{2}(\vect{q}, \vect{p}) = \sum_{i=1}^{D} (q_i - p_i)^{2}
\end{equation}

Pada komputasi berbasis matriks dan GPU, persamaan di atas diekspansi secara aljabar menjadi:
\begin{equation}
d^{2}(\vect{q}, \vect{p}) = \sum_{i=1}^{D} q_i^{2} + \sum_{i=1}^{D} p_i^{2} - 2 \sum_{i=1}^{D} q_i p_i
\end{equation}
atau dalam notasi aljabar linear:
\begin{equation}
d^{2}(\vect{q}, \vect{p}) = \lVert \vect{q} \rVert^{2} + \lVert \vect{p} \rVert^{2} - 2(\vect{q} \cdot \vect{p})
\end{equation}

Suku $2(\vect{q} \cdot \vect{p})$ dapat dipetakan menjadi operasi \keyword{General Matrix-Matrix Multiplication} (GEMM). Operasi ini sangat teroptimasi pada \keyword{hardware}, baik di CPU maupun GPU. Perlu dicatat bahwa ekspansi ini rentan \keyword{catastrophic cancellation} pada \keyword{float32} karena nilai $\lVert \vect{q} \rVert^{2} + \lVert \vect{p} \rVert^{2}$ jauh lebih besar daripada $d^{2}$. Bagian III menjelaskan cara proyek ini menjaga ketepatan hasil.

\section{Hierarki Memori dan \texorpdfstring{\textit{Cache Locality}}{Cache Locality}}

Performa algoritma tidak hanya bergantung pada jumlah instruksi aritmatika, tetapi juga pada kecepatan suplai data ke unit pemrosesan. Arsitektur komputer modern memakai hierarki memori:
\begin{enumerate}[leftmargin=2em]
  \item \keyword{L1 dan L2 Cache}, berukuran puluhan hingga ratusan Kilobita, bersifat \keyword{private} untuk setiap \keyword{core}, dengan latensi beberapa siklus \keyword{clock}.
  \item \keyword{L3 Cache (Last Level Cache)}, berukuran belasan hingga puluhan Megabita dan dipakai bersama seluruh \textit{core} dalam satu cip.
  \item \keyword{Main Memory} (RAM), berkapasitas besar namun berlatensi ratusan siklus \textit{clock}.
\end{enumerate}

Pada implementasi sekuensial yang naif, membaca matriks basis data berulang kali menyebabkan data di L3 Cache terusir sebelum sempat dipakai ulang. Fenomena ini disebut \textit{Cache Thrashing}. Optimasi HPC memanfaatkan prinsip \keyword{Locality of Reference}: \keyword{temporal locality} melalui \textit{Loop Tiling} (cache blocking), dan \keyword{spatial locality} melalui pembacaan data yang berdekatan secara sekuensial agar sejalan dengan \keyword{Cache Line}.

\section{Hukum Amdahl}

Dalam komputasi paralel, \textit{speedup} dibatasi oleh porsi program yang berjalan sekuensial. Hukum Amdahl merumuskan batas ini:
\begin{equation}
S = \frac{1}{(1 - P) + \frac{P}{N}}
\end{equation}
dengan $S$ \textit{speedup} teoretis, $P$ proporsi algoritma yang dapat diparalelkan, $1-P$ proporsi sekuensial, dan $N$ jumlah \keyword{thread}. Hukum ini menjadi dasar bahwa penambahan \textit{core} tidak akan memberi peningkatan linier tanpa batas selama \keyword{overhead} sinkronisasi dan bagian sekuensial (misalnya pengurutan hasil akhir) masih dominan.

\section{Paradigma Pemrosesan Paralel}

\subsection{OpenMP (Shared-Memory Multiprocessing)}
OpenMP adalah API untuk \keyword{shared-memory multiprocessing} di C/C++. Beban \textit{loop} dibagi ke beberapa \textit{thread}. Arahan SIMD (\keyword{Single Instruction, Multiple Data}) memungkinkan kompilator memakai unit vektor perangkat keras (misalnya AVX2) untuk memproses beberapa elemen dimensi dalam satu siklus.

\subsection{CUDA (GPU Acceleration)}
CUDA adalah platform komputasi paralel dari NVIDIA. GPU diarsiteki dengan ribuan \textit{core} kecil untuk eksekusi masif dengan \keyword{throughput} tinggi. Pada optimasi $k$-NN, pemanfaatan \keyword{library} aljabar linear (cuBLAS) dan \textit{shared memory} menjadi kunci untuk meminimalkan ketergantungan \keyword{bandwidth} memori global.

\subsection{MPI (Distributed-Memory Message Passing)}
Ketika ukuran matriks melampaui kapasitas RAM satu \keyword{node}, paradigma terdistribusi diperlukan. MPI adalah standar untuk membagi komputasi lintas proses yang berkomunikasi melalui jaringan. Pola yang dipakai adalah \keyword{broadcast} untuk data kecil (vektor kueri) dan \textit{Gather} untuk mengumpulkan \keyword{top-k} parsial ke proses utama untuk pengurutan final.

\section{Desain Algoritma Sekuensial (Baseline)}

Program \textit{baseline} adalah CPU \keyword{single-thread} tanpa optimasi. Alur kerjanya: memuat matriks kueri dan basis ke memori, menjalankan dua \keyword{nested loop} (luar atas kueri, dalam atas basis), menghitung kuadrat jarak Euclidean tiap pasangan, lalu menyimpan \textit{top-k} dengan \keyword{bounded max-heap} berukuran $k$. Pengukuran memakai pustaka \texttt{chrono} beresolusi tinggi. Selain mode \keyword{batch}, program menyediakan mode \keyword{single-query} yang mencatat waktu tiap kueri untuk menghasilkan nilai p50, p95, dan p99.

\section{Skenario Optimasi 1: Shared-Memory (OpenMP)}

Pendekatan OpenMP diterapkan dalam tiga tahap:
\begin{enumerate}[leftmargin=2em]
  \item \keyword{Loop-level parallelism}: \texttt{\#pragma omp parallel for schedule(dynamic)} pada blok kueri, agar beban terbagi dan ketidakseimbangan berkurang.
  \item \keyword{Vektorisasi SIMD}: \texttt{\#pragma omp simd} pada \textit{loop} dimensi agar unit vektor (AVX) memproses beberapa elemen sekaligus.
  \item \keyword{Cache blocking} (\textit{loop tiling}): baris basis dibaca sekali lalu dipakai ulang untuk sekumpulan kueri, sehingga jumlah pembacaan basis turun dari $Q$ kali menjadi $Q/\text{blok}$ kali.
\end{enumerate}

\section{Skenario Optimasi 2: GPU Acceleration (CUDA)}

Implementasi CUDA menggeser \textit{nested loop} ke perangkat grafis:
\begin{enumerate}[leftmargin=2em]
  \item \keyword{Pemetaan memori}: matriks basis dipindahkan dari \keyword{host} ke VRAM sekali saat \textit{engine} diaktifkan, bukan per kueri.
  \item \keyword{Konversi GEMM}: komputasi $\vect{q} \cdot \vect{p}$ dipetakan menjadi perkalian matriks $\mathbf{Q} \cdot \mathbf{B}^{\top}$ melalui cuBLAS.
  \item \keyword{Penyempurnaan eksak dan reduksi}: kandidat teratas hasil GEMM dihitung ulang dengan rumus eksak $\sum (q_i - p_i)^2$ untuk menjamin hasil identik \textit{baseline}, lalu \textit{top-k} dipilih lewat reduksi di \textit{shared memory}.
\end{enumerate}

Langkah ketiga diperlukan karena ekspansi GEMM kehilangan presisi pada \textit{float32}. Tanpa penyempurnaan, urutan tetangga dapat bergeser dari hasil \textit{baseline}. Dengan penyempurnaan, kriteria kesamaan himpunan hasil (K5) terpenuhi tanpa mengorbankan kecepatan GEMM.

\section{Skenario Optimasi 3: Distributed-Memory (MPI)}

MPI diperlakukan sebagai eksperimen skalabilitas dan pembuktian jalur \keyword{out-of-core}, bukan sebagai \textit{engine} yang ditukar pada demonstrasi antarmuka. Pada satu mesin dengan 4 \textit{core}, empat proses MPI bersaing memperebutkan \textit{core} dan \textit{bandwidth} memori yang sama, sehingga \textit{speedup} MPI tidak diharapkan melampaui OpenMP. Yang diukur adalah penurunan jejak memori per proses dan biaya komunikasi. Langkahnya:
\begin{enumerate}[leftmargin=2em]
  \item \textit{Sharding}: indeks basis dibagi menjadi blok kontigu, dan tiap proses hanya memuat $\lceil N/P \rceil$ baris.
  \item \textit{Broadcast}: proses utama menyiarkan matriks kueri yang berukuran kecil ke seluruh \keyword{worker} dengan \texttt{MPI\_Bcast}.
  \item \keyword{Gather dan merge}: tiap proses menghitung \textit{top-k} lokal, lalu \texttt{MPI\_Gather} mengumpulkan kandidat ke proses utama untuk penggabungan eksak.

\end{enumerate}

\chapter{ANALISIS BOTTLENECK}
% =====================================================================

\section{Memory-bound pada CPU}

Matriks basis $N=500.000$, $D=384$ berukuran sekitar $768$~MB, melampaui LLC 12~MB lebih dari $60$ kali. \textit{Baseline} membaca ulang seluruh matriks untuk setiap kueri. \keyword{Cache tiling} pada OpenMP meningkatkan pemakaian ulang baris basis, sehingga OpenMP 1 \textit{thread} pun sudah $6{,}33\times$ lebih cepat dari \textit{baseline} meskipun hanya memakai satu \textit{thread}. Kenaikan dari 1 ke 4 \textit{thread} menambah \textit{speedup} menjadi $19{,}17\times$, sejalan dengan batas Hukum Amdahl. Profiling roofline efektif (Subbab~\ref{sec:profil}) menunjukkan \textit{effective bandwidth} yang mendekati puncak perangkat keras, mengonfirmasi sifat \textit{memory-bound}.

\section{Compute-bound pada GPU}

GPU GTX 1650 dengan 4~GB VRAM unggul pada \textit{throughput} masif. Dengan memetakan operasi inti ke GEMM cuBLAS dan memindahkan basis ke VRAM sekali, \textit{speedup} batch mencapai $342{,}20\times$. Biaya pemindahan matriks sekitar 60~ms pada PCIe terbagi ke 1.000 kueri, sehingga tidak mendominasi pada mode batch. Karena basis $N=500.000$ ($\approx 768$~MB) plus matriks antara nyaris memenuhi VRAM 4~GB, kernel memecah kueri menjadi \textit{chunk} agar matriks hasil GEMM tetap muat; bila ruang bebas sesaat kurang, ukuran \textit{chunk} diperkecil otomatis.

\section{Komunikasi pada MPI}

Pada satu mesin 4 \textit{core}, proses MPI bersaing memperebutkan \textit{core} dan \textit{bandwidth} memori. Karena itu MPI diposisikan sebagai jalur skalabilitas kapasitas (menurunkan jejak memori per proses), bukan sebagai percepatan latensi. Komunikasi \textit{broadcast} untuk kueri berukuran kecil dan \textit{gather} untuk \textit{top-k} parsial menambah \textit{overhead} yang terukur, namun tetap memberi penurunan waktu komputasi per proses. Pengukuran langsung pada $P=4$ menunjukkan waktu \texttt{MPI\_Gather} dan sinkronisasi hanya sekitar $0{,}04\%$ dari total, sehingga biaya komunikasi negligibel dan batas performa tetap berasal dari \textit{bandwidth} memori bersama, bukan dari komunikasi.

\section{Profil Perangkat Keras}\label{sec:profil}

Listing~\ref{lst:kontrak} menyalin kontrak \texttt{KnnSearchFn} dari berkas nyata \texttt{engine/include/knn\_engine.h}. Semua varian engine (\textit{baseline}, \textit{openmp}, \textit{cuda}, \textit{mpi}) mengimplementasikan tanda tangan yang sama sehingga setara secara antarmuka dan dapat ditukar saat berjalan.

\begin{lstlisting}[style=cppstyle,language=C++,caption={Kontrak \texttt{KnnSearchFn} (sumber: \texttt{engine/include/knn\_engine.h}).},label={lst:kontrak}]
struct Neighbor {
    std::int32_t index;  // indeks baris pada basis vektor
    float        dist2;  // kuadrat jarak Euclidean
};

struct QueryBatch {
    const float* data;   // layout baris: Q x D, float32
    std::size_t  q;      // jumlah query
    std::size_t  d;      // dimensi
};

// basis : matriks N x D, row-major
// out   : Q x k, terurut menaik menurut dist2
// return: 0 sukses, non-nol gagal (mis. VRAM tidak cukup)
using KnnSearchFn = int (*)(const float* basis, std::size_t n,
                            const QueryBatch& batch, std::size_t k,
                            std::vector<Neighbor>& out);
\end{lstlisting}

\noindent Kontrak ini dijaga oleh uji \texttt{scripts/test\_contract.py}: setiap engine harus mengembalikan himpunan \textit{top-k} yang identik dengan \textit{baseline} dan menolak $k$ yang tidak didukung (misalnya $k>64$ pada CUDA) dengan kode galat, bukan hasil yang salah.
